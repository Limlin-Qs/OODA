# ADR-0005 PostgreSQL 持久化、并发与迁移

## 状态

Accepted（2026-09-14）。已实现（2026-10-13 核对）。

## 背景

设备占用、引用完整性、审计同事务和并发冲突必须由权威持久化层保证，不能只依赖前端或应用层先查后写。

## 决策

- 使用 PostgreSQL 作为首版权威数据库。
- 所有 schema 变化使用版本化 SQL 迁移；迁移执行必须有锁或等价机制，禁止手工修改共享环境。
- 使用外键、唯一约束、事务和数据库级原子冲突控制保证设备、成员、借用、预约和审计的一致性。
- 占用冲突采用 PostgreSQL 可证明的排斥约束、锁或等价原子写入，并用真实数据库并发测试验证。
- 具体迁移 runner 属于可替换实施细节，在 G-009 锁定并写入运行说明。

## 替代方案

- SQLite：部署简单，但需要额外证明共享部署下的并发和恢复边界，首版不采用。
- ORM 自动 schema 同步：容易绕过显式迁移审查，首版不作为 schema 权威方式。
- 仅应用层冲突查询：存在竞争窗口，拒绝。

## 后果

可直接利用事务、外键、唯一性和并发控制；需要运行 PostgreSQL，并维护迁移、备份和恢复流程。

## 当前实现与差距（2026-10-13 核对）

已实现事实：PostgreSQL 为权威数据库；`server/migrations/0000–0007` 版本化 SQL 迁移覆盖成员/会话、OIDC 登录状态、设备与审计、审计只追加触发器、借用与幂等键、预约与可用性（`btree_gist` 排斥约束拒绝重叠 active 区间）、通知与尝试记录；约束含外键、CHECK、资产编号唯一、序列号部分唯一、每设备一条 active 借用的唯一索引。迁移 runner（`server/src/migrate.ts`）使用版本表 `_sharework_schema_migrations` + `pg_advisory_xact_lock`，重复执行安全；迁移顺序可追踪。备份/恢复/恢复演练脚本见 `ops/`（ADR-0008）。真实 PostgreSQL 集成测试验证了并发争用、约束拒绝、事务回滚和迁移可重复执行。

现状差距：幂等键表无清理策略；无独立备份存储与保留周期（部署侧待配置）；迁移不承诺向下回滚，破坏性变更流程仅在文档中约定、未经历真实演练；没有生产容量或性能基线数据。

## 不在范围

不决定云数据库提供商、备份产品或个人数据匿名化细节。

## 复核条件

出现多地域写入、跨服务事务或实际容量证据时重新评估。
