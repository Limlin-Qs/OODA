# ADR-0003 服务端权威状态与事务一致性边界

## 状态（Status）

Accepted（2026-09-14）。已确认并在 Phase 1 落地（2026-10-13 核对）；具体后端与数据库产品由 ADR-0004～ADR-0007 选定。

## 背景（Context）

首版计划支持 20–100 名用户共享 50–300 件设备。规模本身不要求复杂分布式系统，但多人借还与预约带来不能靠前端校验解决的正确性要求：

- 同一设备不能被并发双重借出或预约到重叠区间。
- 借用必须有责任人，关键状态变化必须可追溯。
- 权限、时间和业务前置状态不能由浏览器自行声明。
- 网络重试、重复点击和重复调度不能造成重复副作用。
- 外部通知可能失败，不能因此让已经提交的借还事实消失或含糊。

决策时点（2026-09-14）的仓库只有静态 React 模板，没有任何可承担这些职责的服务端、数据库或任务系统。

## 决策（Decision）

采用以下架构边界：

1. **服务端为权威写入边界**：浏览器负责交互和展示；所有设备、借用、预约、成员、权限与审计的权威状态由服务端持久化并校验。客户端缓存不得决定写入是否有效。
2. **一个业务命令一个事务结果**：借出、归还、预约和取消在单个权威事务边界中完成身份/权限校验、前置状态校验、业务写入和审计写入；全部提交或全部回滚。
3. **并发不变量落到持久化层**：占用冲突与唯一性至少由条件写入、唯一/排斥约束、锁或具有同等原子保证的机制保护。应用层“先查再写”和前端禁用按钮只能改善体验，不能作为最终保证。
4. **重试有稳定幂等语义**：对可能因超时重放的状态变更定义幂等标识或等价机制。相同标识和相同请求返回同一业务结果；相同标识但不同内容必须拒绝。
5. **审计与领域事实同事务**：成功写入产生只追加审计，失败写入不产生成功审计。普通应用角色不能更新或删除审计；这不等同于声称数据库管理员也无法篡改。
6. **通知在提交之后可靠处理**：领域事务提交时持久化待发送意图，或采用能提供等价可靠性的机制；外部发送在事务之外执行，可追踪、可重试、可去重。通知失败不回滚领域事实。
7. **保持单一一致性边界**：在当前规模和单工作室范围内，不引入微服务间分布式事务。统计和只读视图可在不影响权威借还判断的前提下最终一致。

## 范围（Scope）

本决策只规定信任、一致性和事务边界，不决定：

- 后端语言、框架或 API 风格。
- PostgreSQL、MySQL、SQLite 或其他具体持久化产品及 ORM。
- 会话、JWT、OAuth 或既有账号体系。
- 邮件、企业微信、飞书或站内信渠道。
- 云、自建或校园内网部署平台。
- 预约端点规则、状态机名称、幂等键有效期和通知频率等产品语义。

这些问题只有在真实备选方案和约束明确后，才按需要建立后续 ADR。

## 替代方案（Alternatives）

- **纯前端/浏览器存储作为权威来源**：无法在多用户之间可靠执行权限、并发互斥和审计，拒绝。
- **服务端 API，但仅靠客户端或应用层预查询防冲突**：两个请求可同时通过检查后写入，无法关闭竞争窗口，拒绝。
- **从首版采用微服务和事件驱动最终一致**：增加跨服务一致性、运维和排障成本，而当前规模没有相应驱动力，拒绝作为首版基线。
- **完整事件溯源作为主存储模型**：审计能力强，但会显著增加建模和查询复杂度；当前只追加审计配合事务写入即可满足已知需求，暂不采用。
- **在外部通知成功后才提交借还事务**：把第三方可用性引入核心事务，容易导致长事务和结果不确定，拒绝。

## 后果（Consequences）

正面影响：

- 业务红线有明确执行位置，前端与服务端职责清晰。
- 可用数据库级原子能力证明并发正确性。
- 审计和通知失败处理不会与业务事实互相矛盾。
- 当前规模下保持单一后端/事务边界，避免不必要的分布式复杂度。

代价与约束：

- 不能只部署静态前端，必须建设可持久化的服务端。
- 需要集成与并发测试，单元测试或手工点击不足以证明正确性。
- 通知会与业务提交解耦，界面需要表达“业务成功但通知待处理/失败”的可能状态。
- 具体数据库必须能证明所需约束；若产品不原生支持区间排斥，需用锁、条件写入或其他等价设计并测试。

## 当前实现（Current Implementation，2026-10-13 核对）

已实现事实：

- 服务端为权威写入边界：Fastify REST/JSON API（ADR-0004），操作者取自服务端会话，不信任客户端自报用户 ID。
- 单命令单事务：`server/src/` 的借用、归还、预约、取消、设备维护命令在 `withTransaction` 内完成权限/前置状态校验、业务写入、审计写入和幂等结果写入。
- 并发不变量落库：`borrow_records` 每设备一条 active 的唯一索引；`reservations` 的 GiST 排斥约束拒绝重叠 active 区间（半开 `[start, end)`）；借用—预约跨表冲突以设备行锁串行化（ADR-0005）。
- 幂等：`(actor_member_id, operation, idempotency_key)` 作用域 + `request_hash` 比对；重放返回原结果，同键不同内容拒绝（`idempotency_conflict`）。
- 审计同事务：`audit_entries` 随业务写入，数据库触发器阻止 UPDATE/DELETE（只追加）。
- 通知解耦：逾期提醒意图与借用事实同事务持久化（`(borrow_id, stage)` 去重），事务外 worker 认领、重试、记录尝试；失败不回滚借还事实（ADR-0007）。
- 验证证据：20 项单测 + 24 项真实 PostgreSQL 集成测试（含并发双借、重叠预约、事务回滚、幂等重放、审计不可变、越权拒绝），2026-10-13 复跑通过。

## 现状差距（Gaps）

- 幂等键无 TTL/清理策略，永久保留；保留期与清理待确认。
- 审计与个人信息的保留、匿名化与法定删除策略仍未定义。
- 预约 `completed` 状态已定义但没有触发入口（无完成命令/自动完成），当前只有取消终态可用。
- 生产部署（HTTPS、OIDC 提供方、独立备份）未完成；Playwright E2E 当前因端口配置漂移不可复现（见根 AGENTS.md §11）。

## 验证要求（Validation）

实现时必须用自动化测试证明：

- 两个并发借出请求最多一个成功。
- 重叠预约以及借用与预约冲突被原子拒绝。
- 事务任一步失败时领域记录与审计均不出现部分提交。
- 相同请求重放不重复生效，相同幂等标识的不同内容被拒绝。
- 通知重复调度只产生允许次数的实际发送，发送失败可追踪并可安全重试。
- 越权或伪造用户 ID 的请求不能改变权威状态。

覆盖状态（2026-10-13）：以上各项均由真实 PostgreSQL 集成测试覆盖并通过；E2E 层面的借出—归还、预约冲突和越权拒绝用例存在，但当前因配置漂移无法复现。

## 重新评估条件（Re-evaluation Triggers）

- 产品转为单机、单操作者且无需共享数据或审计。
- 引入多工作室/多租户、跨地域写入或多个独立服务所有者。
- 出现必须跨系统原子提交的外部流程。
- 法规或安全要求需要防数据库管理员篡改的不可抵赖审计。
- 真实运行数据表明单一事务边界无法满足容量或可用性目标。
